System design & implementation proposal

AI-assisted scheduling and a live-data assistant for True Care System

Add one new module to the existing platform that (a) automatically proposes optimized DSP-to-client schedules and (b) lets office staff, supervisors, and DSPs ask questions and get answers from live data. AI proposes; a supervisor approves. Nothing users already rely on changes.

~13 weeks to full rollout 1.5–2 FTE engineering 1 new module beside the existing NestJS API Propose → approve · no unattended writes Swappable solver · Timefold now, self-hosted later

What we are proposing

One new NestJS module, an MCP server (Model Context Protocol), sits beside the existing API and reuses the database, authentication, and provider isolation already in place. It exposes a small set of tools over live data. Two consumers use those tools: the scheduling optimizer and a Claude-backed assistant ("Selena 2.0") reachable from the portal and the mobile app.

Scheduling optimization runs on Timefold's Field Service Routing API in Phase 1, the fastest path to production, behind a swappable adapter. When volume justifies it, the same adapter can point at a self-hosted open-source solver to cut recurring cost without changing anything users see.

Guiding principles

  • AI proposes; a supervisor approves. No schedule changes without human sign-off.
  • Claude and the solver never touch the database directly and never receive PHI beyond what a task requires.
  • Ship a narrow pilot with one provider first, measure, then expand.
Why this design is HIPAA-defensibleClaude only ever sees what the provider-scoped, audit-logged MCP tools return. The solver receives IDs, coordinates, time windows and skill tags only, never names.

How it works

Two user-facing capabilities, one shared set of tools, one human gate.

Scheduling: propose, review, apply

1. Scheduler asks"Optimize next week for open shifts, prioritize continuity." From the portal chat or a button.
2. Optimizer proposesThe optimize_schedule tool builds a no-PHI request, calls the solver, and stores a proposal (PENDING) with assignments, unassigned visits and reasons.
3. Supervisor approvesSide-by-side current vs. proposed in the portal. Approve, reject, or edit-then-approve. This happens in the existing REST API, not through Claude.
4. Applyapply_schedule commits only an APPROVED proposal, in one transaction, re-validating authorization balances. DSPs get the usual push notification.

Assistant: answers from live data

Office / admin

"What's open this week?" "Which authorizations run out this month?" "Why was this claim rejected?"

Supervisors

"Show me the proposal for next week." "Who can cover Maria's 2 pm call-out?" with ranked, explained candidates.

DSPs (mobile)

"My shifts tomorrow." "Directions to my next visit." "Open shifts I qualify for." "Did my check-in go through?"

Same tools, two entry pointsThe in-app assistant runs Claude in a tool-calling loop against the MCP tools in-process. The same tools are also exposed at POST /mcp for external MCP clients (claude.ai connectors, Claude Desktop, Claude Code) for internal dogfooding. Nothing is duplicated.
02

Options considered

Three ways to add scheduling optimization and AI assistance, evaluated against speed to production, recurring cost, control over constraints, and correctness guarantees.

Recommended for Phase 1 Option 1

Timefold Platform API, wrapped in our own MCP server

Managed, commercial. Timefold's Field Service Routing model assigns visits to workers and routes them to reduce travel and waiting time, with built-in constraints for availability windows, skill matching, multi-worker visits and priorities. Includes a maps service, real-time replanning, and a recommendations API for "who should cover this visit." It explicitly targets home care.

JSON-in/JSON-out over REST, so it plugs straight into NestJS. One customer reports going live with real data in four days. Pricing is quote-based (Spark tier is API-only, managed cloud); a free trial is available.

✓ Fastest to production. Trade-off: recurring subscription cost.
Option 2

Self-hosted open-source solver as a sidecar service

Timefold Solver Community Edition (Apache 2.0, Java/Kotlin, full solver with hard/medium/soft constraints, real-time planning, pinning, no support) or Google OR-Tools (free, Python-first, CP-SAT / routing library). Either runs as a small container the NestJS API calls.

Zero license cost and full control over constraints (PA authorization limits, DSP certifications, continuity of care, overtime).

◐ Cost is 4–8 weeks of engineering to model and tune constraints, plus owning travel-time matrices (OSRM/Google). Planned as Phase 5.
Option 3

LLM-native agent with no solver

Claude reads open shifts, DSP availability, authorizations and distances via MCP tools and proposes assignments directly. Very fast to demo and excellent for the "access information quicker" goal.

But LLMs are not optimizers. For 50+ DSPs and hundreds of visits the result is plausible-but-suboptimal schedules with no guarantees on hard constraints, such as exceeding authorized hours.

✗ Fine as the conversational layer; not fine as the scheduling engine.
03

Recommendation

Option 1 now, with an architecture that lets us swap to Option 2 later. The key design decision: the MCP server is ours and the solver is a replaceable backend.

One MCP server, built with the TypeScript MCP SDK

It lives next to the existing NestJS modules and reuses Prisma plus the provider-isolation and RBAC middleware. It exposes tools such as:

  • get_open_shifts, get_dsp_availability, get_client_authorizations, get_evv_status: read tools over existing tables
  • optimize_schedule(date_range, objectives): builds the solver request from our data, calls the API, returns proposed assignments with an explanation
  • recommend_replacement(visit_id): wraps the recommendations API for call-outs
  • apply_schedule(proposal_id): write tool, gated behind human approval in the portal

The tool contract stays fixed; the backend swaps

Phase 1 (weeks 1–3 of build): Timefold Spark tier via trial, ship to a pilot provider.

Phase 2 (when volume justifies it): replace the tool's implementation with a self-hosted Timefold CE or OR-Tools service. Nothing above it changes: not Claude, not the portal, not the mobile app.

Extending "AI functionality" is just adding toolsBecause every capability is an MCP tool, new features are new tools: summarize_daily_notes, explain_claim_rejection, check_compliance_gaps, query_kpi. The existing Selena assistant becomes a Claude-backed agent calling the same server, so staff get answers from live data rather than canned topic responses.

Architecture

Five layers. Grey is what exists today and stays untouched. Green is the one new Phase 1 piece. Amber dashed is the Phase 2 swap.

Existing New (Phase 1) Phase 2 swap External vendor (under BAA)

Reading the diagram

  • Only one new backend piece. The portal, mobile app, NestJS API, PostgreSQL and Sandata integration are untouched. The AI Orchestrator + MCP Server is one NestJS module beside the existing modules, reusing Prisma and the RBAC / provider-isolation middleware.
  • Claude never talks to the database. It only receives what the MCP tools return, and each tool is provider-scoped and audit-logged. That boundary is what keeps the design HIPAA-defensible.
  • The Solver Adapter is the swap point. Phase 1 calls the Timefold Field Service Routing API; Phase 2 points the same adapter at a self-hosted container. Nothing above that line changes.
  • Writes are gated. apply_schedule only executes after a supervisor approves the proposal in the portal; proposals live in a new schedule_proposals table.
  • One shared chat surface. The Claude assistant appears once in the client layer because it is reachable from both the portal (schedulers, supervisors) and the mobile app (DSPs).

Three things to get straight before writing code

1. Almost no new data. Two new tables, and field-level additions to existing ones.The MCP tools read the shifts, employees, clients, authorizations and visits that already exist. The only new Prisma models are ScheduleProposal and AiToolAudit (in ai.prisma). The real schema work is making sure existing rows carry what the solver needs: coordinates, skills, availability windows, hour caps.
2. The web and mobile apps never call Timefold or Claude.They only call your NestJS API. Timefold is called by TimefoldAdapter inside the API. Claude is called by OrchestratorService inside the API. The GUI talks to two new REST surfaces: a proposals API (list / approve / reject / apply) and one chat endpoint (POST /ai/chat). Neither exists in the skeleton yet; they are Steps 7 and 9 below.
3. One service, two callers.The MCP tools are thin wrappers. Put the real logic (build solver request, create proposal, apply proposal) in ordinary NestJS services. The MCP tool calls the service; the REST controller calls the same service. Then the "Approve & apply" button in the portal and the apply_schedule tool cannot drift apart.

The steps

Step 0 · ½ day

Accounts, keys, branch

  • Anthropic API key (org account, not personal). Timefold trial key and base URL for Field Service Routing.
  • Create branch feat/ai-module. Install: npm i @modelcontextprotocol/sdk zod @anthropic-ai/sdk. Pin exact versions in package.json.
  • Add the six env vars from §15 to .env.example and to staging secrets.
  • Agree role names with whoever owns RBAC: the skeleton uses ADMIN, SCHEDULER, SUPERVISOR, DSP.
Done when: npm run build passes with the new packages installed and env vars documented.
Step 1 · 2–3 days

Schema: new models + field audit + migration

Files: ai.prisma → your schema.prisma.

  • Append ProposalStatus, ScheduleProposal, AiToolAudit to schema.prisma.
  • Audit existing models against what the tools read (table below). Add missing columns. Typical gaps: lat/lng on client service address and on employee home address; skills String[] and availability Json on employee; requiredSkills String[], windowStart/windowEnd, priority on shift; assignedVia and proposalId on shift.
  • Write a one-off geocoding job for client and DSP addresses (Google Geocoding or similar). Store results; do not geocode at request time.
  • prisma migrate dev, then prisma generate.
Done when: migration applied in staging; a report shows ≥95% of pilot-provider clients and DSPs have coordinates; skills taxonomy is a fixed list.
Step 2 · 1 day

Module scaffold and provider scope

Files: ai.module.ts, tool-context.ts, ai-audit.service.ts, mcp-server.factory.ts.

  • Copy src/ai from the zip into the API. Fix the four TODO import paths (Prisma service, Prisma module, Auth module, JWT guard).
  • Import AiModule in AppModule.
  • Confirm what your JWT guard puts on req.user. ToolContext must be built from providerId, id, roles there and nowhere else.
  • Unit-test AiAuditService.wrap(): success writes ok=true with an output hash; a throwing handler writes ok=false with the error and rethrows.
Done when: API boots with AiModule loaded; audit unit tests pass; no tool registered yet does anything.
Step 3 · 3–4 days

Read tools against the real schema

Files: read.tools.ts (5 TODO(prisma) markers).

  • Replace each guessed model/field name with the real one. Keep the select lists minimal; Claude gets IDs and facts, not whole rows.
  • Integration tests per tool with seeded data for two providers.
  • Isolation test suite: for every tool, a user in provider A calling with IDs from provider B gets an empty result or "not found", never B's data. This suite grows with every tool added later.
Done when: five read tools return correct data for the pilot provider in staging; isolation suite green in CI.
Step 4 · 1–2 days

The /mcp endpoint and first live questions

Files: mcp.controller.ts.

  • Mount POST /mcp behind the JWT guard. Add rate limiting (e.g. 60 req/min per user) using whatever throttler the API already uses.
  • Test with MCP Inspector (npx @modelcontextprotocol/inspector) using a staging bearer token: list tools, call get_open_shifts.
  • Connect Claude Desktop or claude.ai as an MCP client for the internal team. This is the Phase 1 exit criterion and the fastest way to find bad tool descriptions.
Done when: an internal user asks "what's open this week for the pilot provider?" in Claude and gets a correct, audited answer.
Step 5 · 3–5 days

Solver adapter: Timefold mapping for real

Files: solver-adapter.ts (keep as is), timefold.adapter.ts, solver.provider.ts.

  • Open the FSR OpenAPI spec for your account and rewrite toTimefold() / fromTimefold() field by field. The skeleton's names are placeholders.
  • Translate objectives (continuity, travel, overtime, fairness weights 0–10) into FSR constraint weights. Continuity of care = "prefer same vehicle for group", group = clientId.
  • Implement recommendReplacement() with the FSR recommendations endpoint (skeleton is a skills-only stub).
  • Contract test: a fixture SolverRequest (10 DSPs, 40 visits, no PHI) round-trips through the adapter against the trial account and yields a SolverResult with assignments and reasons for unassigned.
Done when: the fixture solves in under 2 minutes with a plausible plan; the adapter never sends names or addresses (assert in the test).
Step 6 · 2–3 days

Optimizer tools and shadow runs

Files: optimizer.tools.ts (4 TODO(prisma) markers). New: proposal.service.ts.

  • Move buildSolverRequest(), loadWorkersAndPlan() and the proposal-creation code into a ProposalService. The tool becomes: check role → call service → return summary.
  • Map the remaining TODO(prisma) fields (employee lat/lng, skills, availability, maxWeeklyHours, preferred/excluded clients).
  • Add a scheduled job (nightly, pilot provider only) that calls ProposalService.optimize() for next week. This is shadow mode: proposals are created and compared, nothing is applied.
Done when: a PENDING proposal appears nightly for the pilot provider with assignments, unassigned-with-reasons, and an explanation string.
Step 7 · 3–4 days

Proposals REST API and the approval gate

Files: write.tools.ts. New: proposals.controller.ts in the existing API.

  • Endpoints, all provider-scoped and role-guarded: GET /proposals?status=, GET /proposals/:id (with a current-vs-proposed diff computed server-side), POST /proposals/optimize (button equivalent of the tool), POST /proposals/:id/approve, POST /proposals/:id/reject, POST /proposals/:id/apply.
  • approve sets approvedById, approvedAt, status APPROVED. Only SUPERVISOR / ADMIN. Optionally accept edited assignments (edit-then-approve).
  • Move the transaction in apply_schedule into ProposalService.apply(). Inside the transaction, re-check each assignment's authorization balance and skip or fail with a reason. Both the REST apply endpoint and the MCP apply_schedule tool call this one method.
Done when: Postman flow works end to end: optimize → approve → apply; applying a PENDING proposal is refused; shifts show assignedVia=AI_PROPOSAL.
Step 8 · 5–7 days

Portal: "Proposed schedules" screen (Next.js)

Frontend only; consumes Step 7.

  • List of proposals with status and date range. Detail view: side-by-side current vs. proposed per DSP per day, changed cells highlighted, unassigned visits with the solver's reason.
  • Actions: Approve, Reject (with note), Edit-then-approve (drag a visit to another DSP, then approve), Apply. Apply is a separate click after approval.
  • An "Optimize next week" button that calls POST /proposals/optimize and polls the new proposal.
Done when: the pilot scheduler can review and apply a proposal without engineering help. This unlocks live mode (task 2.6).
Step 9 · 3–4 days

Orchestrator and POST /ai/chat

Files: orchestrator.service.ts. New: ai-chat.controller.ts.

  • Add a controller: POST /ai/chat body { history: ChatTurn[] }, guard = JWT, builds ToolContext the same way as /mcp, returns the assistant's reply text. Stateless: the client sends the full history.
  • Set CLAUDE_MODEL to the current Claude model id and verify the Anthropic SDK types match the installed version.
  • Extend the system prompt with role-specific guidance (a DSP sees only their own shifts; a scheduler is told proposals need approval). Keep the 8-round cap and add a per-request token budget.
  • Log every chat turn (user, provider, tokens in/out, tools called) for the cost dashboard in Step 12.
Done when: a curl to /ai/chat with "what's open tomorrow?" returns an answer that cites shift IDs from the read tools.
Step 10 · 5–8 days

Chat surfaces: portal panel and mobile "Ask"

The skeleton is a single NestJS module (src/ai, ~750 lines across 15 files) that drops into the existing API. Here is how the files map to the green boxes in the architecture diagram.

mcp-server.factory.ts is the heart of it

It builds a fresh McpServer per request, bound to a ToolContext (providerId, userId, roles) taken from the existing JWT guard. Because scope is captured in a closure at construction time, no tool can execute without a provider ID, and write tools are only registered if the caller is ADMIN or SUPERVISOR.

Two entry points share the same tools

Propose-then-approve is enforced in code

  • Provider scope comes from the authenticated user (the existing guard), never from the client.
  • Solver payloads carry IDs, coordinates, time windows and skill tags only, no names or PHI.
  • Writes are two-step: optimize_schedule → proposal row (PENDING) → supervisor approves in portal → apply_schedule(proposal_id) commits.

import { Injectable } from '@nestjs/common';
import { createHash } from 'crypto';
import { PrismaService } from '../../prisma/prisma.service'; // TODO(prisma): your path
import { ToolContext } from '../scope/tool-context';

@Injectable()
export class AiAuditService {
  constructor(private readonly prisma: PrismaService) {}

  /** Wrap any tool handler so every call is timed, logged, and provider-tagged. */
  async wrap<T>(ctx: ToolContext, toolName: string, input: unknown, fn: () => Promise<T>): Promise<T> {
    const t0 = Date.now();
    try {
      const out = await fn();
      await this.write(ctx, toolName, input, t0, true, out);
      return out;
    } catch (e: any) {
      await this.write(ctx, toolName, input, t0, false, undefined, e?.message);
      throw e;
    }
  }

  private write(ctx: ToolContext, toolName: string, input: unknown, t0: number, ok: boolean, out?: unknown, error?: string) {
    return this.prisma.aiToolAudit.create({
      data: {
        providerId: ctx.providerId, userId: ctx.userId, channel: ctx.channel, toolName,
        input: input as any,
        outputHash: out ? createHash('sha256').update(JSON.stringify(out)).digest('hex') : null,
        durationMs: Date.now() - t0, ok, error,
      },
    });
  }
}

 * Phase 1 backend: Timefold Field Service Routing API.
 * Flow: POST dataset -> poll status -> GET solution. Field names below are

@Injectable()
export class TimefoldAdapter implements SolverAdapter {
  readonly name = 'timefold' as const;
  private readonly log = new Logger(TimefoldAdapter.name);
  private readonly base = process.env.TIMEFOLD_BASE_URL!;
  private readonly key = process.env.TIMEFOLD_API_KEY!;

  async solve(req: SolverRequest): Promise<SolverResult> {

    const jobId = await this.submit(payload);
    await this.waitUntilDone(jobId, 120_000);
    const solution = await this.get(`/route-plans/${jobId}`);
    return this.fromTimefold(jobId, solution);
  }

  async recommendReplacement(req: ReplacementRequest): Promise<ReplacementCandidate[]> {
    // TODO: call the FSR recommendations endpoint with current plan + orphaned

      .filter((c) => req.visit.requiredSkills.every((s) => c.skills.includes(s)))
      .map((c) => ({ workerId: c.id, score: 0, reasons: ['skills match (stub)'] }));
  }

  private toTimefold(req: SolverRequest) {
    return {
      config: { run: { name: `tcs-${req.providerId}-${req.rangeStart}` } },
      vehicles: req.workers.map((w) => ({
        id: w.id,
        startLocation: [w.homeLocation.lat, w.homeLocation.lng],
        skills: w.skills,
        shifts: w.availability.map((a, i) => ({ id: `${w.id}-${i}`, start: a.start, end: a.end })),
      })),
      visits: req.visits.map((v) => ({
        id: v.id,
        location: [v.location.lat, v.location.lng],
        serviceDuration: `PT${v.durationMinutes}M`,
        timeWindows: v.timeWindows,
        requiredSkills: v.requiredSkills,
        priority: v.priority,
        pinnedVehicleId: v.pinnedWorkerId,
        group: v.clientId, // "prefer same vehicle for group" models continuity of care
      })),
      // TODO: translate req.objectives into FSR constraint weights
    };
  }

  private fromTimefold(jobId: string, sol: any): SolverResult {
    const assignments = (sol.vehicles ?? []).flatMap((veh: any) =>
      (veh.itinerary ?? []).map((it: any) => ({
        visitId: it.id, workerId: veh.id, start: it.arrivalTime, end: it.departureTime,
        travelMinutes: it.travelTimeFromPreviousMinutes,
      })),
    );
    const unassigned = (sol.unassignedVisits ?? []).map((u: any) => ({
      visitId: u.id, reason: u.reason ?? 'no feasible assignment',
    }));
    return { jobId, assignments, unassigned, score: sol.score, explanation: sol.scoreExplanation };
  }

  // ---- http --------------------------------------------------------------
  private async submit(body: unknown): Promise<string> {
    const r = await this.post('/route-plans', body);
    return r.id;
  }

  private async waitUntilDone(jobId: string, timeoutMs: number) {
    const t0 = Date.now();
    while (Date.now() - t0 < timeoutMs) {
      const s = await this.get(`/route-plans/${jobId}/status`);
      if (['SOLVING_COMPLETED', 'TERMINATED'].includes(s.solverStatus)) return;
      if (s.solverStatus === 'FAILED') throw new Error(`Timefold job ${jobId} failed`);
      await new Promise((res) => setTimeout(res, 2000));
    }
    throw new Error(`Timefold job ${jobId} timed out`);
  }

  private async post(path: string, body: unknown) {
    const res = await fetch(this.base + path, {
      method: 'POST', headers: { 'Content-Type': 'application/json', 'X-API-KEY': this.key },
      body: JSON.stringify(body),
    });
    if (!res.ok) throw new Error(`Timefold ${path} -> ${res.status}`);
    return res.json();
  }

  private async get(path: string) {
    const res = await fetch(this.base + path, { headers: { 'X-API-KEY': this.key } });
    if (!res.ok) throw new Error(`Timefold ${path} -> ${res.status}`);
    return res.json();
  }
}

  async chat(ctx: ToolContext, history: ChatTurn[]): Promise<string> {

    const [clientT, serverT] = InMemoryTransport.createLinkedPair();
    await server.connect(serverT);
    const client = new Client({ name: 'truecare-orchestrator', version: '0.1.0' });
    await client.connect(clientT);

    try {
      const { tools } = await client.listTools();
      const anthropicTools = tools.map((t) => ({ name: t.name, description: t.description ?? '', input_schema: t.inputSchema as any }));
      const messages: Anthropic.MessageParam[] = history.map((h) => ({ role: h.role, content: h.content }));

      for (let i = 0; i < 8; i++) { // hard cap on tool-call rounds
        const resp = await this.anthropic.messages.create({
          model: this.model, max_tokens: 2000, system: this.systemPrompt(ctx), tools: anthropicTools, messages,
        });
        messages.push({ role: 'assistant', content: resp.content });
        if (resp.stop_reason !== 'tool_use') {
          return resp.content.filter((b) => b.type === 'text').map((b: any) => b.text).join('\n');
        }
        const results: Anthropic.ToolResultBlockParam[] = [];
        for (const block of resp.content) {
          if (block.type !== 'tool_use') continue;
          const r = await client.callTool({ name: block.name, arguments: block.input as any });
          results.push({ type: 'tool_result', tool_use_id: block.id, content: (r.content as any[]).map((c) => c.text ?? '').join('\n') });
        }
        messages.push({ role: 'user', content: results });
      }
      return 'I could not finish that request within the allowed number of steps.';
    } finally {
      await client.close(); await server.close();
    }
  }

  private systemPrompt(ctx: ToolContext) {

      'You are the True Care System assistant for a home care / I/DD provider.',

      'Scheduling changes are proposals; tell the user a supervisor must approve them in the portal.',
      'Be concise. Cite the specific shift/client/DSP ids you relied on. Never guess data you did not retrieve.',
    ].join(' ');
  }

# True Care System — AI Orchestrator + MCP Server (skeleton)

Drop-in NestJS module (`src/ai`) that adds:

1. **MCP Server** (`/mcp` endpoint, Streamable HTTP) exposing provider-scoped tools
   over your existing Prisma models.
2. **Solver Adapter** interface with a Timefold Field Service Routing implementation
   (Phase 1) and a self-hosted stub (Phase 2). The tool contract never changes.
3. **AI Orchestrator** — a Claude tool-calling loop that the portal/mobile chat
   surface calls. Claude only ever sees what MCP tools return.
4. **Audit + approval** — every tool call is logged; `apply_schedule` only runs
   against a proposal a supervisor approved in the portal.
